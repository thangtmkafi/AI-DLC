Part 1

Orientation

Quick install

One terminal command installs or upgrades AI-DLC in your project folder. Auto-detects mode, moves any legacy files into 00-knowledge/references/, downloads the latest release from GitHub.

macOS / Linux

curl -fsSL https://raw.githubusercontent.com/Kafivn/KORA/main/tools/install.sh | bash

Windows (PowerShell)

iwr -useb https://raw.githubusercontent.com/Kafivn/KORA/main/tools/install.ps1 -OutFile install.ps1
.\install.ps1

Don't run /init. Kiro already auto-loads AGENTS.md + inclusion: always steering files on every session start; /init is redundant on AI-DLC projects. Use kafi-aidlc-onboarding steering instead — auto-detects current stage and loads the right role + prompt.

Full installation guide: KAFI-Installer-Guide.html

What is KAFI AI-DLC

An AI-driven software development workflow. The AI agent drafts artifacts, asks clarifying questions, and generates code. Humans review, decide, and approve at every gate. Three properties make it work:

Adaptive

The agent runs only the stages that add value for this project. Simple projects skip ceremony; complex ones get the full process.

Artifact-based

Every decision lives in a markdown file in the repo, not in chat. Git is the audit trail. Reviews happen on files.

Human-at-the-gates

The agent never proceeds past a phase boundary without explicit approval. Every stage ends with a 2-option gate.

Two modes

Mode is auto-detected at Workspace Detection. The user can override at any time.

LiteStandard
TriggerGreenfield + Vision + Tech Env both readyBrownfield OR inputs missing OR legacy doc needs mapping

Reverse EngineeringSkippedRuns (brownfield only)
Doc count typical12–1520–35
Best forNew internal tool, MVPExtending existing systems, regulated, multi-team

Your first session

Five steps from cloning the package to producing the first artifact.

Step 1

Set up the project

Unzip kafi-aidlc-v03-kiro.zip into your project root. You should see AGENTS.md, README.md, and the .kiro/ directory. Then create 00-knowledge/ with your BRD, PRD, architecture docs, conventions, open items.

Step 2

Open Kiro IDE

Kiro auto-loads AGENTS.md plus every .kiro/steering/ file with inclusion: always front-matter — the common process rules, KAFI design system, and audit-trail extension. The agent announces detected mode (Lite or Standard) and proposes the first stage.

Step 3

Drive your stage

Type #pm, #ba, #sa, etc. in chat to load your role guide, or paste the full starter prompt from the Introduction document. The agent loads the steering file (inclusion: manual) and produces a plan with [Answer]: tags.

Step 4

Review and approve

Read the artifacts the agent writes to aidlc-docs/. Fill in answers, edit files directly if needed, request changes. Approve when ready.

How to start a session

After install, the kafi-aidlc-onboarding steering file handles session start. It scans your project, detects current AI-DLC stage, loads the right role guide, and substitutes a stage-appropriate prompt template. You don't paste starter prompts manually anymore.

How to use: in Kiro chat, type: #kafi-aidlc-onboarding (manual inclusion via Kiro's #filename syntax).

What the steering does: scans 00-knowledge/ and aidlc-docs/, classifies project position against the 17-stage workflow (Mode B detection), reads the matching prompt template from .kiro/steering/kafi-aidlc-onboarding-prompts/, substitutes placeholders, and starts the session.

Stage → Role → Prompt mapping

The steering picks the right template for you. This table is for transparency — edit templates to customize agent behavior at your KAFI project level.

Template files are plain Markdown with placeholders (PROJECT, Stage, unit-name, etc.) that the steering substitutes from your detected context. Audit or customize via your IDE.

Phase by phase

Phase 1 · Standard mode only

Pre-Inception

Get the inputs Inception needs. Lite mode skips this entirely.

Utility

Entry Router

Conditional PM + BA

Inputs

  • User's initial message
  • 00-knowledge/ context
→

Outputs

  • aidlc-docs/inception/discovery/
    entry-router-questions.md
  • audit.md entry with routing decision

What happens

  1. Three multi-choice questions: what do you want to do, what do you have, any hard constraints.
  2. Map answers to a recommended sub-flow (A / B / C / D).
  3. Present recommendation; user confirms or picks another.
Skip when
User named a sub-flow explicitly. A document is attached (Document Validator runs instead).
Utility

Document Validator

Conditional BA

Inputs

  • source.md (attached doc)
→

Outputs · discovery/validation/

  • <source>-review.md
  • <source>-questions.md (if confidence < 0.6)

What happens

  1. Consent-first — ask "Run validation on <file>?" Wait for yes.
  2. Classify document as BRD / PRD / Vision / story-pack / Mixed with confidence score.
  3. Score against the matching class's rubric (Pass / Partial / Missing).
  4. Flag vague language ("seamless", "scalable" without numbers, "robust").
  5. Flag cross-class leakage (BRD with embedded stories, PRD with biz case prose).
  6. Recommend a sub-flow with reason.
Never modifies the source document
Always produces sibling review/questions files. The team owns the original.

Sub-flow B

fill-gaps

When one missing PM or SA

Inputs

  • Whichever file exists
  • .kiro/templates/vision.md
  • .kiro/templates/technical-environment.md
→

Outputs · discovery/

  • vision.md (if was missing)
  • technical-environment.md (if was missing)
  • <doc>-draft-questions.md

What happens

  1. Identify which document is missing.
  2. Walk the corresponding template section by section. For each section: derive from existing inputs if possible; ask via [Answer]: tag if not.
  3. Each completed section gets a mini approval before moving on.
  4. When the file is complete, resume the main workflow.
Sub-flow C

map-existing

When legacy doc BA

Inputs

  • Legacy BRD / PRD source file
  • .kiro/templates/vision.md
→

Outputs · discovery/

  • vision.md (mapped)
  • source-appendix.md (original preserved)
  • fit-check.md (rubric report)
  • vision-gap-questions.md
  • technical-environment.md
  • validation/<source>-review.md

What happens

  1. Document Validator runs first if not already.
  2. Fit-check against Vision rubric — present / partial / missing per section.
  3. Map source content to Vision Document structure; preserve original as source-appendix.md.
  4. Generate gap questions for partial / missing sections.
  5. After answers, write vision.md; then produce technical-environment.md (using fill-gaps logic).
Sub-flow D

author-from-brief

When intent only BA

Inputs

  • User's brief or intent message
  • .kiro/templates/vision.md
→

Outputs

  • aidlc-docs/inception/discovery/vision.md
  • aidlc-docs/inception/discovery/technical-environment.md
  • aidlc-docs/ba-authoring/<feature>/plan.md
  • aidlc-docs/ba-authoring/<feature>/questions.md

What happens · 7-step process

  1. Template resolution — pick template (KAFI standard unless overridden).
  2. Requirement parsing — extract feature name, deliverables, languages from brief.
  3. Gap analysis — ask drafting depth (Minimal / Standard / Comprehensive) and critical gap questions.
  4. Drafting plan — checkbox plan with dependencies; BA approves before drafting.
  5. Drafting execution — section by section, ticking checkboxes, mini-approvals.
  6. Translation — if multi-language, draft both versions in parallel.
  7. BA review gate — full document review; loop back only on named sections if changes requested.
Phase 2 · Both modes

Inception

Determine WHAT to build and WHY. Nine stages — three always run, six are conditional.

Stage 1

Workspace Detection

Always AI agent Both modes

Inputs

  • ai-dlc/project.md
  • workspace filesystem
  • aidlc-state.md (if resuming)
→

Outputs

  • aidlc-docs/aidlc-state.md
  • aidlc-docs/audit.md entry
  • Mode announcement (Lite or Standard)

What happens

  1. Check for aidlc-state.md — if found, resume.
  2. Detect existing code in src/ → greenfield or brownfield.
  3. Check for Vision + Tech Env in discovery/ → inputs ready or not.
  4. Decide mode: Lite if greenfield + inputs ready, Standard otherwise.
  5. Announce mode and proposed next stage.
Stage 2

KB Context Loading

Always AI agent Both modes

Inputs · 00-knowledge/

  • architecture/* (per context-pins)
  • open-items.md
  • conventions/naming.md
  • conventions/architecture-boundaries.md
  • phases.md
→

Outputs

  • Context loaded into agent memory
  • Summary presented to user
  • (no files written)

What happens

  1. Read ai-dlc/context-pins.md if exists; otherwise use defaults from project.md.
  2. Load pinned KB sections.
  3. Load open items, naming conventions, architecture boundaries, phase definitions.
  4. Verify last_verified on KB files (warn if > 90 days).
  5. Present summary: sections loaded, open items active, conventions in effect.
Context-pin budget
Max 4k tokens of KB per unit. If your context-pins exceed → the unit is too large; split it.
Stage 3

Reverse Engineering

Conditional SA Std + brownfield

Inputs

  • 00-knowledge/architecture/
  • src/ (existing code)
→

Outputs · inception/reverse-engineering/

  • business-overview.md
  • architecture.md
  • code-structure.md
  • component-inventory.md
  • dependencies.md
  • technology-stack.md

What happens

  1. Plan part — write reverse-engineering-plan.md with focus areas and questions; user approves.
  2. Generate 6 outputs, KB-first. Cite KB sections explicitly.
  3. Cross-reference code only to verify or fill gaps.
  4. If code contradicts KB → flag as open item, don't silently update either.
  5. Surface any unclear interface contracts via open-items protocol.
Skip when
Lite mode · greenfield · existing artifacts present and recent.
Stage 4

Requirements Analysis

Always PM + BA Both modes

Inputs

  • aidlc-docs/inception/discovery/vision.md
  • aidlc-docs/inception/discovery/technical-environment.md
  • 00-knowledge/product/ (BRD/PRD)
  • 00-knowledge/open-items.md
→

Outputs · inception/requirements/

  • requirements.md (REQ-NN IDs with citations)
  • requirement-verification-questions.md

What happens

  1. Read Vision + Tech Env + KB sections.
  2. Run intent analysis — what's actually being asked for?
  3. Determine depth: Minimal / Standard / Comprehensive based on scope.
  4. Generate REQ-NN entries. Cite KB and Vision sections per requirement.
  5. For requirements touching open items, emit canonical line: Open — pending [owner]. Never fabricate.
  6. Write clarifying questions to a separate file for ambiguous areas.
Watch for
Vague NFRs slipping in — "should be fast", "user-friendly". Push them to Stage 11 (NFR Requirements) with measurable thresholds, don't accept here.
Stage 5

User Stories

Conditional BA User-facing only

Inputs

  • aidlc-docs/inception/requirements/requirements.md
  • aidlc-docs/inception/discovery/vision.md (personas)
  • .kiro/templates/user-story.md
→

Outputs · inception/user-stories/

  • stories.md (US-NN IDs, G/W/T ACs)
  • personas.md

What happens · 2-part stage

  1. Plan part: generate story plan with checkboxes and questions on persona detail, AC format, role naming.
  2. BA approves plan.
  3. Execution part: generate stories with US-NN IDs.
  4. Each story cites KB sections and REQ-NN dependencies.
  5. Acceptance criteria in Given/When/Then format.
  6. Use neutral roles (user, operator) until project taxonomy is confirmed.
Skip when
Pure internal refactor · infrastructure-only changes · documentation-only updates.
Stage 6

Workflow Planning

Always PM Both modes

Inputs

  • All prior Inception artifacts
  • 00-knowledge/phases.md
→

Outputs · inception/plans/

  • execution-plan.md

What happens

  1. Assess project shape: user-facing? multi-component? multi-unit? per-unit NFR concerns?
  2. Decide which subsequent stages run, at what depth.
  3. Run phase-discipline check: flag anything outside the active phase from phases.md.
  4. Write execution-plan.md with stage-by-stage decisions + reasoning.
  5. PM can request inclusion/exclusion of specific stages before approving.
Stage 7

Product Design

Conditional Designer UI involved

Inputs

  • aidlc-docs/inception/user-stories/
  • .kiro/steering/kafi-design-system.md
  • 00-knowledge/design-system/ (if project has overrides)
→

Outputs · inception/product-design/

  • user-flows.md
  • information-architecture.md
  • wireframes/
  • screen-designs/
  • interaction-specs.md
  • accessibility-notes.md

What happens

  1. Load the KAFI design system skill (.kiro/steering/kafi-design-system.md). Apply tokens, typography, components, patterns.
  2. Define user flows and journey maps from stories.
  3. Produce information architecture.
  4. Create key screen designs at appropriate fidelity.
  5. Define interaction specs (states, transitions, edge cases) for Code Generation to consume.
  6. Cover empty / error / loading states — not just happy path. WCAG 2.1 AA minimum.
Watch for
Custom components when design system covers it · mockups missing negative states · designs ignoring IA · ungrounded UX assumptions.
Stage 8

Application Design

Conditional SA Both modes

Inputs

  • aidlc-docs/inception/requirements/
  • aidlc-docs/inception/user-stories/
  • aidlc-docs/inception/product-design/ (if UI)
  • 00-knowledge/conventions/architecture-boundaries.md
→

Outputs · inception/application-design/

  • application-design.md (consolidated)
  • components.md
  • component-methods.md
  • services.md
  • component-dependency.md
  • + ADRs to adrs/

What happens

  1. Domain modeling — entities, value objects, aggregates.
  2. Component design with clear boundaries per project's architecture-boundaries extension.
  3. Define method signatures and service contracts.
  4. Map dependencies (internal + external).
  5. Run boundary verification — any cross-boundary call requires an ADR.
  6. Open ADRs for every trade-off (sync/async, tech pick, data shape, consistency model, build vs buy).
Skip when
Changes stay within existing component boundaries (lightweight extension only).
Stage 9

Units Generation

Conditional SA Multi-unit

Inputs

  • aidlc-docs/inception/application-design/
  • aidlc-docs/inception/user-stories/
→

Outputs · inception/application-design/

  • unit-of-work.md (UNIT-NN definitions)
  • unit-of-work-dependency.md
  • unit-of-work-story-map.md
  • + per-unit folders created under construction/

What happens · 2-part stage

  1. Plan part: decomposition plan with grouping strategy and parallel-build questions; SA approves.
  2. Execution part: generate UNIT-NN definitions.
  3. Map every story to a unit — no orphans.
  4. Document inter-unit dependencies; no cycles.
  5. Create per-unit folders with intent.md and pinned-context.md placeholders.
Skip when
Single-unit project (the whole app is one unit).

Construction

Stage 10 · per-unit

Functional Design

Conditional BA + SA

Inputs

  • aidlc-docs/inception/application-design/
  • aidlc-docs/inception/user-stories/ (this unit's stories)
  • aidlc-docs/inception/product-design/interaction-specs.md (if UI)
→

Outputs · construction/{unit}/functional-design/

  • business-logic-model.md
  • business-rules.md
  • domain-entities.md
  • frontend-components.md (if UI)

What happens

  1. Extract business logic from this unit's stories into business-logic-model.md.
  2. Formalize validation rules and decision tables in business-rules.md.
  3. Refine domain entities from Application Design with concrete properties + invariants.
  4. If UI: specify frontend component hierarchy, props, local state, events.
  5. Run extensions compliance summary (audit-trail hooks, privacy fields).
Stage 11 · per-unit

NFR Requirements

Conditional SA

Inputs

  • aidlc-docs/construction/{unit}/functional-design/
  • aidlc-docs/inception/discovery/technical-environment.md
  • aidlc-docs/inception/requirements/ (NFR hints)
→

Outputs · construction/{unit}/nfr-requirements/

  • nfr-requirements.md
  • tech-stack-decisions.md

What happens

  1. Identify NFR categories that apply: performance · scalability · availability · security · observability · accessibility · maintainability · compliance.
  2. For each, write measurable thresholds — ms, percentile, load profile.
  3. Reject vague language ("fast", "scalable", "robust") without numbers.
  4. Document technology stack choices and rationale (cache choice, queue choice, etc.).
  5. KAFI-wide NFRs (audit, privacy via extensions) automatically applied.
Watch for
Vague thresholds slipping in. No "should be fast" — require p95/p99 latency, throughput, load profile. SA owns this pushback (no QA in v0.3).

Stage 14 · per-unit

Code Generation

Always Developer

Inputs

  • aidlc-docs/construction/{unit}/functional-design/

Code goes to src/ only. NEVER inside aidlc-docs/. The aidlc-docs/construction/{unit}/code/ folder holds markdown summaries — not source files.

Part 3

Reference

Document types

The workflow produces 19 canonical document types across four phases. Each entry below names the stage that produces it, who owns it, what it contains, and whether a pre-built template exists in .kiro/templates/. Templates marked ★ are starting scaffolds the agent uses; the team's project knowledge fills in the specifics.

Project overrides: drop a same-named file in 00-knowledge/templates/ and it wins over the KAFI standard. Project taxonomy or stricter formats can be enforced this way without modifying the kafi-aidlc-v03-kiro.zip package. Traceability IDs: REQ-NN · US-NN · UNIT-NN · ADR-NN · NFR-*-NN.

Pre-Inception

Vision Document

Pre-Inception · Stage 0 PM ★ template
aidlc-docs/inception/discovery/vision.md

The "what + why" of the project. Defines goals, target users, scope IN and scope OUT, measurable success criteria, and constraints. Every downstream stage refers back to this for grounding.

Contains: problem statement · target users / personas · in-scope capabilities · out-of-scope items · success metrics (numbers) · constraints · open questions for stakeholders.

Technical Environment

Pre-Inception · Stage 0 SA ★ template
aidlc-docs/inception/discovery/technical-environment.md

The technical constraints the system must live within: stack, cloud target (or "open"), integration touchpoints, prohibited libraries, regulatory environment. Tells the SA what tools are on the table before design starts.

Contains: programming languages · framework choices · cloud / on-prem target · existing systems to integrate with · prohibited or required libraries · regulatory environment · network topology constraints.

Inception

Reverse Engineering Pack

Stage 3 SA brownfield only
aidlc-docs/inception/reverse-engineering/ (6 files)

Documents what the existing system looks like before extending it. KB-first: the SA cites the architecture KB first, then cross-references the code only to verify or fill gaps. If code contradicts KB, both are flagged as open items.

Contains: business-overview.md · architecture.md · code-structure.md · component-inventory.md · dependencies.md · technology-stack.md.

Requirements

Stage 4 PM + BA ★ template
aidlc-docs/inception/requirements/requirements.md

The contract between business intent and the system. REQ-NN entries with citations back to Vision and BRD. Functional capabilities, regulatory constraints, architectural constraints, phase scope, and explicit out-of-scope.

Contains: functional capabilities (REQ-NN) · regulatory constraints (REQ-REG-NN) · architectural constraints (REQ-ARCH-NN) · phase constraints (REQ-PHASE-NN) · out of scope · open items.

User Stories & Personas

Stage 5 BA user-facing only ★ template (single story)
aidlc-docs/inception/user-stories/stories.md + personas.md

Stories in INVEST format with Given/When/Then acceptance criteria. Every story cites the REQ-NN it implements and the persona it serves. Roles stay neutral until the project's role taxonomy is confirmed.

Contains: US-NN entries · acceptance criteria (G/W/T) · persona definitions · REQ-NN traceability · open items where role taxonomy is unsettled.

Execution Plan

Stage 6 PM
aidlc-docs/inception/plans/execution-plan.md

The PM's call on which subsequent stages run, at what depth, with what gating discipline. Reflects project shape (UI? multi-component? multi-unit?) and phase scope. Approved by PM before any downstream stage begins.

Contains: stages included · stages skipped · depth per stage (minimal/standard/comprehensive) · gating model · phase compliance notes.

Product Design Pack

Stage 7 Designer UI involved only
aidlc-docs/inception/product-design/ (6 files / folders)

UX deliverables specific enough for Code Generation to consume directly. References the KAFI design system for every component; custom components require justification. Empty, error, and loading states are covered, not just happy path.

Contains: user-flows.md · information-architecture.md · wireframes/ · screen-designs/ · interaction-specs.md · accessibility-notes.md.

Application Design Pack

Stage 8 SA ★ template (consolidated + components)
aidlc-docs/inception/application-design/ (5 files)

High-level architecture — components, methods, services, dependencies. ADR-driven: every architectural trade-off opens an ADR. Boundary verification against the project's architecture-boundaries.md happens here.

Kiro spec mode

Alongside the full AI-DLC lifecycle, Kiro ships a native lightweight pattern for feature-scoped work: .kiro/specs/<feature-name>/. Use it when a single feature warrants explicit requirements / design / tasks artifacts without driving the entire 17-stage workflow.

FilePurposeFed from AI-DLC
spec.jsonMetadata — name, owner, status, AI-DLC stage mapping—
requirements.mdUser stories + EARS acceptance criteria + constraints + out-of-scopeInception stages 4 + 5 outputs
design.mdArchitecture, components, data model, cost, decisionsInception stages 7-9 + Construction 10-13 outputs
tasks.mdCheckboxed delivery plan with milestones + risksConstruction stage 14-15 outputs

A blank template lives at .kiro/specs/_template/. Copy and rename when starting a feature:

cp -r .kiro/specs/_template .kiro/specs/my-feature
# edit spec.json with feature name + owner
# fill in requirements.md from Inception output

Two modes, complementary not competing:

  • AI-DLC mode (this handbook). Full lifecycle, 17 stages, role-driven. Use for new projects from intent to production.
  • Kiro spec mode. Single feature, lightweight three-file pattern. Use when a feature has well-scoped boundaries and the team prefers Kiro's native idiom.

Recommended pattern. Run AI-DLC Inception to produce Vision + Requirements + Application Design. Then for each Unit of Work, generate a Kiro spec folder so the construction team has a focused workspace. Inception artifacts become source-of-truth references in requirements.md; the per-unit Kiro spec captures the build details.

Loading Kiro specs in chat: reference any file with #requirements, #design, #tasks — Kiro resolves to the nearest spec folder by context.

AI Review Checklist

Soft enforcement — warnings reported in completion summary, team decides whether to proceed.

Critical · warning if NO

  • Grounded — claims reference real KB, code, or docs in this repo
  • No secrets — no credentials, tokens, keys, PII, customer data
  • Scope respected — output stays within requested change
  • Reversible — changes easy to revert; risky ops have rollback note
  • Human-decidable — architectural / trade-off choices called out for a human

Quality · informational

  • Matches house style (linters, formatters, naming)
  • Negative and edge cases covered
  • Errors handled
  • Observable (logs, metrics, traces where they matter)
  • Docs touched (README/ADR/aidlc-docs updated when appropriate)
Risk-shaped review
For changes touching auth · money · PII · external contracts · infrastructure (IaC) → flag for dual review (SA + relevant role). For IaC: plan-before-apply, destructive ops flagged.
