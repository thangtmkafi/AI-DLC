Introduction

Giới thiệu

In KAFI's AI-Driven Development Lifecycle (AI-DLC), every output — Vision, requirements, user stories, design specs, code — lives as a file in a Git repository. Reviews happen on files. Approvals are tracked as pull requests. Git is the audit trail. This guide teaches you everything you need to participate, even if you have never written a line of code.

Trong quy trình AI-DLC của KAFI, mọi sản phẩm — Vision, requirements, user story, design spec, code — đều tồn tại dưới dạng file trong một Git repository. Việc rà soát diễn ra trên file. Việc phê duyệt được ghi nhận qua pull request. Git chính là nhật ký kiểm toán. Tài liệu này hướng dẫn mọi điều bạn cần để tham gia, ngay cả khi bạn chưa từng viết một dòng code nào.

Phần 4 hướng dẫn thao tác hàng ngày trong công cụ bạn chọn — Git Extensions, Fork, hoặc dòng lệnh. Phần 5 là tra cứu xử lý sự cố. Đổi ngôn ngữ và giao diện sáng/tối bất cứ lúc nào bằng nút phía trên.
PART 1

Why Git matters for non-developers

Vì sao Git quan trọng với người phi-lập trình

Six people (PM, BA, SA, Designer, Dev, DevOps) plus an AI agent work on one repo. Without a system, three things break: people overwrite each other, decisions get lost, and "which version is final?" becomes a daily question. Git fixes all three.

Sáu vai trò (PM, BA, SA, Designer, Dev, DevOps) cùng một AI agent làm việc trên cùng một repo. Không có hệ thống thì ba điều sẽ vỡ: mọi người ghi đè lên nhau, quyết định bị mất, và câu hỏi "bản nào là bản cuối?" trở thành chuyện thường ngày. Git giải quyết cả ba.

Parallel work without collisions

Làm song song không đụng nhau

PM drafts Vision while BA writes requirements while Designer mocks screens. Each has their own branch — a private timeline — so edits never overwrite each other.

PM viết Vision, BA viết requirement, Designer mock màn hình — đồng thời. Mỗi người làm trên một nhánh riêng (timeline riêng) nên các chỉnh sửa không ghi đè lẫn nhau.

Every decision auditable

Mọi quyết định đều có dấu vết

Each change is a commit with author, timestamp, and message. The whole history is preserved — you can replay how the project arrived at its current state.

Mỗi thay đổi là một commit kèm tác giả, thời điểm, và mô tả. Toàn bộ lịch sử được giữ lại — bạn có thể tua lại để hiểu vì sao dự án đến được trạng thái hiện tại.

A clear gate between draft and final

Có cửa rõ ràng giữa nháp và bản cuối

Work-in-progress lives on a branch. To make it "official", you open a Pull Request — a review checkpoint. Only approved PRs merge into main. main is always trusted.

Bản đang làm sống trên nhánh. Để biến nó thành "chính thức", bạn mở Pull Request — một chốt rà soát. Chỉ PR đã được duyệt mới hoà vào main. main luôn là bản đáng tin cậy.

PART 2

Core Git concepts

Khái niệm Git cốt lõi

Nine ideas. Each has a one-paragraph explanation and a diagram. Read them in order — they build on each other.

Chín khái niệm. Mỗi cái có một đoạn giải thích và một sơ đồ. Đọc theo thứ tự — chúng xây dựng dần lên nhau.

1 · Repository (repo)

1 · Repository (kho code, gọi tắt là repo)

A repository is a folder that Git is tracking. Whatever is inside — markdown files, design specs, code, images — Git records every version of every file. A repo has two faces: the local copy on your laptop, and the remote copy on GitHub (the shared source of truth).

Một repository là một thư mục được Git theo dõi. Bên trong có gì — file markdown, design spec, code, hình ảnh — Git đều ghi lại mọi phiên bản của mọi file. Một repo có hai mặt: bản local trên máy bạn, và bản remote trên GitHub (nguồn chân lý chung).

Local repo ↔ Remote repo · synced via push and pull
Repo local ↔ repo remote · đồng bộ qua push và pull
In KAFI Trong KAFI Every project lives in a GitHub repository owned by KAFI. The Transformation Office creates the repo, sets folder ownership (CODEOWNERS), and seeds it with the AI-DLC skeleton (CLAUDE.md, aidlc-rule-details/, etc.). You clone it to your laptop to start working. Mỗi dự án nằm trong một repository GitHub thuộc sở hữu KAFI. Văn phòng Chuyển đổi tạo repo, gán chủ sở hữu thư mục (CODEOWNERS), và seed sẵn bộ khung AI-DLC (CLAUDE.md, aidlc-rule-details/, …). Bạn clone về máy để bắt đầu làm việc.

2 · The four zones

2 · Bốn vùng

A file lives in one of four places at any moment. Understanding these zones is the single most important concept in Git — every command moves a file from one zone to the next.

Một file tại mỗi thời điểm sẽ nằm ở một trong bốn vùng. Hiểu các vùng này là khái niệm quan trọng nhất trong Git — mọi lệnh đều đẩy file từ vùng này sang vùng kế.

Working Dir → Staging → Local Repo → Remote Repo · with pull bringing remote changes back
Working Dir → Staging → Local Repo → Remote Repo · và pull đưa thay đổi từ remote về
Zone Vùng Analogy Ví dụ ví von Command to enter Lệnh để đưa vào
1 · Working Directory 1 · Working Directory Your desk · open documents Mặt bàn · tài liệu đang mở Just edit the fileCứ chỉnh file Just edit the fileCứ chỉnh file
2 · Staging Area 2 · Staging Area A shopping basket · what you've picked out Giỏ hàng · những món bạn đã chọn git add git add
3 · Local Repository 3 · Local Repository A photo album · permanent snapshots on your laptop Album ảnh · các snapshot vĩnh viễn trên máy bạn git commit git commit
4 · Remote Repository 4 · Remote Repository Cloud backup · what teammates see Cloud backup · cái mà đồng nghiệp thấy git push git push
The most common mistake Lỗi thường gặp nhất "I committed my changes but my teammate doesn't see them." Committing only puts changes in zone 3 (local). To share, you must push to zone 4 (remote). The reverse is also true: a teammate's commit isn't on your laptop until you pull. "Tôi đã commit rồi nhưng đồng nghiệp không thấy." Commit chỉ đưa thay đổi vào vùng 3 (local). Muốn chia sẻ phải push sang vùng 4 (remote). Ngược lại cũng vậy: commit của đồng nghiệp chưa nằm trên máy bạn cho tới khi bạn pull.

3 · Commit

3 · Commit

A commit is a saved snapshot of every file in the repo at a single moment, plus a short message explaining why. Each commit has a unique fingerprint (hash) like a3f5c2e. Commits are immutable — once made, they don't change. The full history of commits is the project's narrative.

Một commit là một snapshot toàn bộ file trong repo tại một thời điểm, kèm một mô tả ngắn giải thích vì sao. Mỗi commit có một dấu vân tay duy nhất (hash) kiểu a3f5c2e. Commit là bất biến — đã tạo thì không thay đổi nữa. Toàn bộ lịch sử commit chính là dòng kể của dự án.

Each commit is a permanent snapshot · the chain is the project history
Mỗi commit là một snapshot vĩnh viễn · chuỗi commit chính là lịch sử dự án

Anatomy of a commit (KAFI format)

Cấu trúc một commit (theo định dạng KAFI)

Subject:  Stage 4: Requirements — REQ-01 to REQ-12

Body:     Produced: requirements.md (12 REQs)
          KB cited: arch/treasury.md §3, glossary.md
          Open items: L2 role taxonomy

Footer:   Related: REQ-01..REQ-12, ADR-03

# Hash assigned by Git: 9c0a2d4...
# Author + timestamp recorded automatically
Why messages matter Vì sao message quan trọng Three months later, when someone asks "why does requirement REQ-07 exist?", the commit message is how you find out. Lazy messages like "update" or "fix" are unhelpful. The KAFI format always names the stage and the artifact produced. Ba tháng sau, khi có người hỏi "vì sao tồn tại REQ-07?", commit message là cách bạn tìm ra. Message lười biếng kiểu "update" hoặc "fix" vô dụng. Định dạng KAFI luôn gọi tên stage và artifact được tạo ra.

4 · Branch (nhánh)

4 · Branch (nhánh)

A branch is a parallel timeline of commits. The main timeline is called main — the official, approved version. When you start work, you create a new branch off main, do your commits there, and merge back only when reviewed. Branches let multiple people work simultaneously without stepping on each other.

Một branch là một timeline commit song song. Timeline chính gọi là main — bản chính thức, đã được duyệt. Khi bắt đầu việc, bạn tạo một nhánh mới rẽ ra từ main, commit ở đó, và chỉ gộp về sau khi đã rà soát. Branch cho phép nhiều người làm song song mà không đụng nhau.

BA's requirements branch was reviewed and merged back · Designer's branch is still open
Nhánh requirements của BA đã được rà soát và gộp về · nhánh của Designer vẫn đang mở

Why branch at all?

Vì sao phải dùng nhánh?

Without branches, every change goes straight into main. Half-finished work breaks the official version. With branches, you experiment freely on your own timeline — your half-finished Vision draft can't affect anyone else.

Không có nhánh, mọi thay đổi đi thẳng vào main. Việc dở dang sẽ làm vỡ bản chính thức. Có nhánh, bạn thử nghiệm thoải mái trên timeline riêng — Vision viết dở của bạn không ảnh hưởng ai khác.

A branch is a label, not a copy

Branch là một nhãn, không phải bản sao

Creating a branch is instant. Git doesn't duplicate files — it just adds a pointer ("this name = this commit"). That's why teams can have dozens of branches without bloating the repo.

Tạo branch là tức thì. Git không sao chép file — nó chỉ thêm một con trỏ ("tên này = commit này"). Vì vậy đội có thể có hàng chục branch mà repo vẫn không phình to.

5 · Checkout — switching lanes

5 · Checkout — chuyển làn

Checkout means "switch my working directory to a different branch (or commit)". The files on disk physically change to match whatever you check out. It's like flipping the train track — you stay in the same station, but the next car arriving is from a different line.

Checkout nghĩa là "chuyển working directory của tôi sang một nhánh khác (hoặc commit khác)". Các file trên đĩa sẽ vật lý thay đổi để khớp với cái bạn checkout. Giống như bẻ đường ray — bạn vẫn ở cùng một ga, nhưng toa kế tiếp đến là của tuyến khác.

HEAD moves to a different branch — your files change to match it
HEAD chuyển sang nhánh khác — file của bạn thay đổi theo
Save before you switch Lưu trước khi chuyển Git won't let you check out a different branch if you have uncommitted changes in working dir that would be overwritten. Either commit them first, or stash them (a temporary set-aside). Both tools in Part 4 prompt you for this automatically. Git sẽ chặn không cho checkout sang nhánh khác nếu working dir của bạn còn thay đổi chưa commit và sẽ bị ghi đè. Hoặc bạn commit trước, hoặc stash lại (đặt tạm sang một bên). Cả hai công cụ ở Phần 4 đều nhắc bạn tự động.

6 · Push, Pull, Fetch

6 · Push, Pull, Fetch

Three commands move commits between your laptop and GitHub. Push sends your local commits up. Fetch downloads remote commits without changing your files (read-only check). Pull = fetch + merge: it downloads and applies the remote changes to your current branch.

Ba lệnh chuyển commit giữa máy bạn và GitHub. Push đẩy commit local lên trên. Fetch tải commit remote về nhưng không đụng file của bạn (chỉ ngó). Pull = fetch + merge: vừa tải xuống vừa áp dụng vào nhánh đang đứng.

Sync flow between your laptop and GitHub
Luồng đồng bộ giữa máy bạn và GitHub
Command Lệnh What it does Tác dụng When you use it Khi nào dùng
git push git push Upload local commits to GitHub Đẩy commit local lên GitHub End of stage · ready to open PR Kết thúc stage · sẵn sàng mở PR
git fetch git fetch Check what's new on GitHub (no changes to your files) Kiểm tra xem GitHub có gì mới (không động vào file của bạn) Curious about teammates' progress Muốn xem đồng nghiệp tiến tới đâu

7 · Merge — joining timelines

7 · Merge — gộp các timeline

Merge takes the commits from one branch and joins them into another. The destination branch (usually main) gets a new commit — the "merge commit" — that has two parents: the previous tip of main and the tip of the merged branch. After merging, the branch's work is now part of the official history.

Merge lấy commit từ một nhánh và nhập vào nhánh khác. Nhánh đích (thường là main) nhận một commit mới — "merge commit" — có hai bố mẹ: đầu cũ của main và đầu của nhánh được merge. Sau khi merge, công việc trên nhánh đó đã thành một phần lịch sử chính thức.

After merge: branch commits live inside main's history forever
Sau merge: commit của nhánh sống trong lịch sử main mãi mãi
In KAFI you rarely run merge yourself Trong KAFI bạn hiếm khi tự chạy merge The merge into main happens automatically when a Pull Request is approved on GitHub. You merge only in two cases: (1) bringing fresh main changes into your own branch while you work, (2) resolving a conflict. Việc merge vào main diễn ra tự động khi Pull Request được duyệt trên GitHub. Bạn chỉ phải merge thủ công trong hai trường hợp: (1) kéo thay đổi mới từ main về nhánh của bạn khi đang làm, (2) xử lý conflict.

8 · Pull Request (PR) — the review gate

8 · Pull Request (PR) — cửa rà soát

A Pull Request is a formal proposal on GitHub: "please review my branch and, if approved, merge it into main." It's a conversation around the diff — reviewers comment line-by-line, request changes, or approve. In KAFI, every stage ends by opening a PR.

Một Pull Request là lời đề nghị chính thức trên GitHub: "vui lòng rà soát nhánh của tôi và, nếu được, hãy merge vào main." Nó là một cuộc trao đổi quanh diff — reviewer comment từng dòng, yêu cầu sửa, hoặc duyệt. Trong KAFI, mỗi stage kết thúc bằng việc mở PR.

PR life cycle · review happens between push and merge
Vòng đời PR · rà soát diễn ra giữa push và merge

What a KAFI PR looks like

Một PR theo chuẩn KAFI trông thế nào

Title:   Stage 4: Requirements — closes gate

Body:
  Outputs:
  - aidlc-docs/inception/requirements/requirements.md (12 REQs)
  - aidlc-docs/inception/requirements/verification-questions.md (3)

  KB cited: arch/treasury.md §3, glossary.md
  Open items: L2 role taxonomy

# Reviewers (from CODEOWNERS): PM + BA team
# Required checks: parity check, link check
Reviewers comment on files, not in chat Reviewer comment trên file, không phải trong chat PR comments are anchored to specific lines. That means feedback like "this REQ doesn't have acceptance criteria" stays attached to the exact requirement forever. Compare that to a Slack thread that vanishes in 48 hours. Comment trên PR được gắn vào dòng cụ thể. Nghĩa là feedback kiểu "REQ này thiếu acceptance criteria" sẽ dính vào đúng requirement đó mãi mãi. So với một thread Slack biến mất sau 48 giờ.

9 · Conflict — when two branches edit the same line

9 · Conflict — khi hai nhánh sửa cùng một dòng

A conflict happens when Git can't automatically combine two changes — usually because two people edited the same line of the same file. Git pauses the merge and asks you to choose. Conflicts feel scary the first time but the resolution is mechanical: read both versions, pick the right one (or combine), save, continue.

Một conflict xảy ra khi Git không thể tự động hợp hai thay đổi — thường vì hai người sửa cùng một dòng của cùng một file. Git tạm dừng việc merge và hỏi bạn chọn. Lần đầu thấy conflict có thể sợ nhưng cách xử lý đơn giản: đọc cả hai phiên bản, chọn đúng (hoặc kết hợp), lưu, tiếp tục.

Git marks both sides with <<<<<<, ======, >>>>>> · you choose the final wording
Git đánh dấu cả hai phía bằng <<<<<<, ======, >>>>>> · bạn chọn bản cuối

Read both sides

Đọc cả hai phía

The text between <<<<<< HEAD and ======= is yours. Below ======= down to >>>>>> is the other version.

Đoạn giữa <<<<<< HEAD và ======= là của bạn. Phía dưới ======= đến >>>>>> là bản kia.

Decide intent

Quyết định ý đúng

Pick one, both, or rewrite. Talk to the other author if you don't know which is correct. Don't guess.

Chọn một bên, cả hai, hoặc viết lại. Hỏi tác giả bên kia nếu bạn không chắc bản nào đúng. Đừng đoán.

Delete the markers

Xoá các dấu

Remove <<<<<<, ======, >>>>>> lines completely. Save the file. Then commit — that finishes the merge.

Xoá hoàn toàn các dòng <<<<<<, ======, >>>>>>. Lưu file. Rồi commit — vậy là kết thúc merge.

KAFI · audit.md is special KAFI · audit.md là trường hợp đặc biệt aidlc-docs/audit.md is append-only and will conflict on almost every merge. The rule is simple: keep both sides in chronological order, then delete the markers. Both tools in Part 4 have a one-click option for this. aidlc-docs/audit.md là append-only và sẽ luôn conflict ở hầu hết các merge. Quy tắc đơn giản: giữ cả hai phía theo thứ tự thời gian, rồi xoá các dấu. Cả hai công cụ ở Phần 4 đều có nút một-bấm để xử lý.
PART 3

The KAFI branch model

Mô hình nhánh của KAFI

Generic Git is just plumbing. KAFI AI-DLC adds three concrete rules that make six roles plus an AI agent work in one repo without collisions:

Git nguyên bản chỉ là đường ống. KAFI AI-DLC thêm ba quy tắc cụ thể để sáu vai trò cùng AI agent có thể làm việc trên một repo không đụng nhau:

Rule 1

Quy tắc 1

stage = branch

stage = branch

Each AI-DLC stage gets its own branch. Stage 4 → stage/4-requirements. Stage 7 → stage/7-design. The branch name is the stage's audit trail.

Mỗi stage AI-DLC có một branch riêng. Stage 4 → stage/4-requirements. Stage 7 → stage/7-design. Tên branch chính là dấu vết kiểm toán của stage.

Rule 2

Quy tắc 2

gate = pull request

gate = pull request

A stage's 2-option completion message ("Request Changes / Continue") is materialized as a PR review. The PR is the gate.

Thông điệp hoàn tất 2-lựa chọn ("Request Changes / Continue") của một stage được hiện thực hoá thành cuộc rà soát PR. PR chính là cửa kiểm soát.

Rule 3

Quy tắc 3

merge = approval

merge = approval

A PR can only merge into main after CODEOWNERS sign-off. Once merged, that stage is officially closed.

PR chỉ được merge vào main sau khi CODEOWNERS duyệt. Một khi đã merge, stage đó chính thức đóng.

Each commit's subject names the stage and what was produced; the body lists KB citations and any open items surfaced. Reviewers should be able to read just the subject line and understand what shipped.

Subject mỗi commit gọi tên stage và sản phẩm tạo ra; body liệt kê các trích KB và open items phát sinh. Reviewer chỉ cần đọc subject là hiểu cái gì đã ra đời.

Subject:  Stage [N]: [stage name] — [brief outcome]

Body:     Produced: [files / IDs]
          KB cited: [section refs]
          Open items: [list or "none"]

The command line is universal, scriptable, and reads exactly the same on every machine. Even if you prefer a GUI day-to-day, learning the seven commands below pays off — you'll understand what the GUI is doing under the hood, and you can recover any repo over SSH if something breaks.

Dòng lệnh phổ quát, script được, và đọc giống nhau trên mọi máy. Dù bạn thích GUI hàng ngày, học bảy lệnh dưới đây vẫn rất đáng — bạn sẽ hiểu GUI đang làm gì bên trong, và có thể cứu repo qua SSH nếu có gì hỏng.

One-time setup

Setup một lần

# Tell Git who you are — used on every commit
git config --global user.name  "Your Name"
git config --global user.email "you@kafi.vn"

# Saner defaults
git config --global init.defaultBranch main
git config --global pull.rebase false       # merge on pull (safer for non-devs)
git config --global core.autocrlf input     # Mac/Linux · use 'true' on Windows

# Clone the KAFI project
git clone git@github.com:kafi/<project>.git
cd <project>

PART 5

Troubleshooting · the things that scare new users

Xử lý sự cố · những lỗi hay làm người mới hoảng

Nine common scenarios with the safe recovery for each. None of these will lose data if you follow the steps. When in doubt, stop and ask your tech lead — but read this first.

Chín tình huống thường gặp và cách khôi phục an toàn cho từng cái. Nếu làm theo, không cái nào làm mất dữ liệu. Khi nghi ngờ, dừng và hỏi tech lead — nhưng đọc phần này trước đã.

"I committed but my teammate doesn't see it"

"Tôi commit rồi nhưng đồng nghiệp không thấy"

Cause: commits sit in zone 3 (local) until you push.

Nguyên nhân: commit ở vùng 3 (local) cho tới khi bạn push.

Fix: git push (or click Push in your GUI). Then your teammate runs git pull.

Sửa: git push (hoặc bấm Push trong GUI). Đồng nghiệp chạy git pull.

"Git won't let me checkout — uncommitted changes"

"Git không cho checkout — còn thay đổi chưa commit"

Cause: the target branch would overwrite your edits.

Nguyên nhân: branch đích sẽ ghi đè lên bản sửa.

Fix: either commit (git add + git commit), or stash temporarily (git stash) — then checkout.

Sửa: hoặc commit (git add + git commit), hoặc stash tạm (git stash) — rồi mới checkout.

"My push was rejected — non-fast-forward"

"Push bị từ chối — non-fast-forward"

Cause: someone pushed to the same branch while you were working.

Nguyên nhân: ai đó đã push lên cùng branch trong lúc bạn đang làm.

Fix: git pull, resolve any conflict, then git push again. Never use --force.

Sửa: git pull, xử lý conflict nếu có, rồi git push lại. Không bao giờ dùng --force.

"I committed to the wrong branch"

"Tôi commit nhầm branch"

Cause: forgot to checkout before working.

Nguyên nhân: quên checkout trước khi làm.

Fix (if not pushed yet): create the right branch from where you are (git checkout -b correct-branch), then on the wrong branch: git reset --soft HEAD~1 to undo the commit but keep changes.

Sửa (nếu chưa push): tạo branch đúng từ chỗ bạn đang đứng (git checkout -b correct-branch), rồi trên branch nhầm: git reset --soft HEAD~1 để hoàn tác commit nhưng vẫn giữ thay đổi.

"I broke audit.md with conflicts"

"audit.md của tôi đầy conflict marker"

Cause: every session appends to audit.md; merges always conflict here.

Nguyên nhân: mỗi phiên đều append vào audit.md; merge luôn conflict tại đây.

Fix: CLI: git checkout --merge aidlc-docs/audit.md. Or in GUI: pick "keep both sides" in the merge tool. Append-only — never overwrite.

Sửa: CLI: git checkout --merge aidlc-docs/audit.md. Hoặc trong GUI: chọn "giữ cả hai phía" trong merge tool. Append-only — không bao giờ ghi đè.

"I want to undo my last commit"

"Tôi muốn huỷ commit vừa rồi"

Not pushed yet: git reset --soft HEAD~1 — keeps your file changes, unstages the commit.

Chưa push: git reset --soft HEAD~1 — giữ thay đổi file, gỡ commit ra.

Already pushed: git revert <hash> — creates a new commit that undoes it. Safe on shared branches.

Đã push: git revert <hash> — tạo commit mới đảo ngược commit cũ. An toàn trên branch dùng chung.

"I want to discard all my uncommitted changes"

"Tôi muốn vứt hết thay đổi chưa commit"

Fix: git restore . (CLI) or right-click → "Discard changes" (GUI). Make sure you really mean it — this is irreversible.

Sửa: git restore . (CLI) hoặc chuột phải → "Discard changes" (GUI). Hãy chắc chắn — không khôi phục được.

"I accidentally deleted a branch"

"Tôi lỡ xoá nhánh"

Fix: git reflog shows every HEAD movement. Find the last commit on the deleted branch, then git checkout -b recovered <hash>.

Sửa: git reflog hiển thị mọi lần HEAD di chuyển. Tìm commit cuối của branch đã xoá, rồi git checkout -b recovered <hash>.

"GitHub says my PR has conflicts"

"GitHub báo PR có conflict"

Fix: on your laptop, checkout your branch, git pull origin main, resolve conflicts locally, commit, push. The PR updates automatically.

Sửa: trên máy bạn, checkout branch của mình, git pull origin main, xử lý conflict, commit, push. PR tự cập nhật.

The escape hatch · git reflog Lối thoát hiểm · git reflog Git keeps a private log of every change to HEAD for ~90 days, even ones you "lost". Running git reflog in your repo's terminal is the closest Git has to a time machine. Anything you commit can be recovered with it. Take a deep breath. Git lưu một log riêng cho mọi lần HEAD đổi trong khoảng 90 ngày, kể cả những lần bạn "mất". Chạy git reflog trong terminal của repo là cỗ máy thời gian gần nhất mà Git có. Mọi thứ đã commit đều có thể khôi phục từ đây. Hít một hơi sâu.

Mental model

Mô hình tư duy

  • 1 stage = 1 branch. Each AI-DLC stage gets its own branch named stage/{N}-{kebab}.1 stage = 1 branch. Mỗi stage AI-DLC một branch tên stage/{N}-{kebab}.
  • 1 PR = 1 gate. The stage completion message becomes the PR title + body.1 PR = 1 gate. Message hoàn tất stage trở thành title + body của PR.
  • main is sacred. Never commit directly. Always branch, PR, merge.main là thiêng liêng. Không bao giờ commit thẳng. Luôn branch, PR, merge.
  • Pull before you start. Every session opens with checkout main → pull → new branch.Pull trước khi bắt đầu. Mỗi phiên mở đầu bằng checkout main → pull → branch mới.
  • audit.md keeps both sides. Append-only file — on conflict, keep both blocks chronologically.audit.md giữ cả hai phía. File append-only — khi conflict, giữ cả hai khối theo thứ tự thời gian.
