AI-DLC v1.0

A methodology for building software with an AI agent doing the work and a human deciding what is acceptable.

Audience · Leadership · PM/PO · BA · SA · Tech Lead · Dev · QA · DevOps/SRE

What it is

AI-DLC is a methodology, not a tool. What you install into a project is prose, templates and two reference registries — no executable code at all. The agent reads it and behaves accordingly; there is no checker to put in CI, and there has not been one since v0.3.

It supports Codex, Claude Code and Kiro from one canonical source. The three adapters are generated projections, not three hand-maintained copies, so they cannot drift apart.

The one sentence that explains the rest

The agent produces the work product; a human decides whether it is acceptable.

Everything else follows. The agent is never an approver, so authority always rests with a person. Because the producer and the decider are already different parties, no rule anywhere asks for a second human — one person holding four roles approves their own project's gates and nothing is marked for it. And because the agent does the producing, the human's job is judgment at gates rather than typing.

Four commands

The entire daily surface, the same for every role:

  • /kafi-aidlc-onboarding — how do I start, or join?
  • /kafi-aidlc-status — where are we?
  • /kafi-aidlc-next — what do I do next?
  • /kafi-aidlc-check — is anything wrong?

Installation is a prompt, not a script. You paste it, the agent resolves a verified public release, inspects your project, and shows a plan. Nothing is created, moved or deleted until you approve that plan in your own words.

What the project looks like

A project is one folder, not one repository. The folder itself is unversioned scaffolding, rebuildable from a manifest in the Hub:

<project>/
├── project-hub/      docs plane · one git repo · the canonical state
├── components/       code plane · one git repo per component
└── ops/              ops plane · SRE-owned

Everything a project decides lives in the Project Hub as Markdown. Component repositories hold code and reference the Hub; they never establish a parallel copy of requirements or approvals.

What is applicable is resolved, not assumed

A profile — Entry × Scope × Delivery relationship × Work type — decides which stages, artifacts and gates apply. A question irrelevant to your profile is never asked, and an artifact that is Not Applicable is never reported missing. Two operating models sit on top: Continuous for flowing slices, Phase-Gated for baselines and change requests.

Two rules worth knowing before you start

Evidence or ask. The agent cites the artifact, revision or commit behind every claim. Where evidence is absent it records the question and asks rather than inventing an answer. It never fabricates identity, authority, approvals, test results or commit SHAs.

No finding blocks the work. A detector that finds something wrong reports what it found, what would fix it, and in what order — and the work continues. Refusing to proceed never made a broken install safe; it moved the cost onto the person trying to get something done. The one exception is a test failure inside the scope you just changed.
