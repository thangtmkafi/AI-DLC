The KAFI AI-DLC Workflow

An introduction for project leads and teams. How we ship software with AI as the drafter and humans as the deciders. This unified doc covers both Claude Code and Kiro IDE editions — edition-specific paths and commands are called out inline.

Audience Leadership · PMs · POs · BAs · SAs · Designers · Devs · DevOps

Software development at KAFI is becoming AI-first. The AI agent drafts artifacts, asks clarifying questions, and generates code. Humans review, decide, and approve at every gate.

AI-DLC isn't about replacing the team. It's about making every role more focused: PMs spend more time on scope decisions, not formatting. BAs spend more time on edge cases, not boilerplate. Devs spend more time reviewing and refining, not typing out scaffolding. Every artifact is in git. Every decision is logged. Every output is reviewable.

Methodology & approach v0.8

Since v0.3, AI-DLC matured from a linear spec-writer into a spec-driven, test-verified, audited lifecycle. Four pillars define how KAFI ships software with AI now.

1 · Spec-driven for FE and BE

Every artifact derives from an upstream spec. BE from data-model.md (ENT-NN) + functional-design; FE from design-tokens.md + uiux-spec.md + view-model.md (MVVM). Traceability: PRD → REQ → ENT → US → UNIT → TC → ADR.

2 · Documents kept up-to-date

The kafi-doc-sync skill keeps aidlc-docs/ current with src/; Stage 14c audits doc-currency. Docs are the live contract, not write-once artifacts.

3 · Audit & verifiable at each gate

Process step 5.5 spec-conformance trace-back (mechanical); AI Review Checklist Hard/Soft split; Stage 14c 5 blocking sub-checks (code · token discipline · UI fidelity · test coverage · flow conformance). Every gate is a verification point, not a rubber stamp.

4 · Spec-driven, test-verified

QA authors test-plan.md + test-cases.md (Stage 10b) from specs; Dev generates unit test code (Stage 14b); audit checks coverage (Stage 14c). Tests are the executable form of the spec. (Execution itself is the project's CI/local choice.)

New since v0.3? See KAFI-AIDLC-Whats-New.html for the v0.4 → v0.8 highlights + how to upgrade.

Quick install

One terminal command drops AI-DLC into your project folder. The installer auto-detects whether to install fresh or upgrade an existing version, moves any legacy files into 00-knowledge/references/, and downloads the latest release from GitHub. Cross-platform: macOS, Linux, Windows.

macOS / Linux

curl -fsSL https://raw.githubusercontent.com/thangtmkafi/AI-DLC/main/tools/install.sh | bash

Windows (PowerShell)

iwr -useb https://raw.githubusercontent.com/thangtmkafi/AI-DLC/main/tools/install.ps1 -OutFile install.ps1
.\install.ps1

Don't run /init. Both editions auto-load the workflow file on every session start (Claude Code → CLAUDE.md; Kiro → AGENTS.md + inclusion: always steering files). /init is non-destructive but redundant on an AI-DLC project. The kafi-aidlc-onboarding skill/steering replaces it — see below.

Full installation guide with all flags, scenarios, and troubleshooting: KAFI-Installer-Guide.html

How a session actually works

Every stage follows the same rhythm. Humans decide; the agent drafts and asks; nothing proceeds without explicit approval.

Step 1
Human
Sets intent
PM/PO names what to build. Or a stage owner reviews prior artifacts and decides what's next.
Step 2
AI agent
Drafts + asks
Agent writes a plan with checkboxes and questions in a `[Answer]:` file. Asks measurable, non-vague questions.
Step 3
Human
Reviews + answers
Stage owner fills `[Answer]:` tags, edits artifacts directly if needed, or asks for changes.
Step 4
Human
Approves gate
Two-option message: Request Changes or Continue to Next Stage. No silent progress.

Roles in your project team

Seven human roles. Each role has a skill file the agent loads when you're driving a stage that role owns. QA joined in v0.7 (test planning + conformance audit). No Security or Compliance role — compliance is enforced automatically via extensions.

Product Owner

PM / PO

Owns intent and scope. Authors or validates the Vision Document. Decides what runs and what gets cut.

Drives: Requirements Analysis · Workflow Planning · Pre-Inception D (author from brief)

Business Analyst

BA

Translates intent to requirements and stories. Pushes back on vague language. Uses neutral roles until taxonomy is confirmed.

Drives: Requirements · User Stories · Functional Design · Pre-Inception B/C/D

Solution Architect

SA

Architecture, NFRs, ADRs. Guardian of KB boundaries. Pushes for measurable NFR thresholds.

Drives: Reverse Engineering · App Design · NFR Requirements · NFR Design · Units Generation

Product Designer

Designer

UX flows, screen specs, interaction patterns. References the KAFI design system — custom components require justification.

Drives: Product Design (only stage UX-led)

Developer

Dev

Pairs with the AI agent on production code (Stage 14a) AND unit test code (Stage 14b · v0.8). Reviews the plan, verifies the build, owns build instructions.

Drives: 14a Production Code · 14b Unit Test Code · Build

QA NEW v0.7

QA

Authors test plan + test cases as documentation (Stage 10b) and runs the 4-sub-check conformance audit (Stage 14c · BLOCKING). Does NOT write test code (Dev does at 14b) and does NOT execute tests (project's CI/local choice).

Drives: 10b Unit Test Planning · 14c Conformance Audit

DevOps / SRE

DevOps

Maps logical components to concrete services. Owns deployment topology and monitoring — Operations (Stage 16/17) formalized in v0.8 with deployment + monitoring runbooks.

Drives: Infrastructure Design · Deployment (16) · Monitoring (17)

After install, you don't manually pick a role or paste a starter prompt. The kafi-aidlc-onboarding skill handles routing — it scans your project, detects current AI-DLC stage, loads the right role guide, and starts the session with a stage-appropriate prompt template.

Working together with git

Seven roles plus the AI agent share one repo. The workflow's gates and branches stay in lockstep so parallel work doesn't collide and the audit history is clean. Three rules: stage = branch, gate = pull request, merge = approval.

One branch per stage

Inception stages get their own branch — stage/4-requirements, stage/8-app-design. Construction work groups under unit/UNIT-NN-name. Pre-Inception sub-flows: pre-inception/route-D-vision.

Gate = pull request

The 2-option completion message becomes the PR. Reviewer is the next-stage role or the SA (depending on what's being merged). Approve and merge = gate passed.

Append-only audit log

aidlc-docs/audit.md is append-only on every branch. On merge conflicts: keep both — never overwrite. The full audit history is the TT 96/2020 record.

Where files live

The folder structure is the contract. The team feeds inputs into 00-knowledge/; the workflow writes outputs into aidlc-docs/, adrs/, and src/. Every stage knows exactly which folders it reads from and writes to.

Principle · Manual KB (pre-KAI Atlas)

PO, PM, and BA manually copy project context files into the KB folder

BRD, PRD, architecture diagrams, glossaries, system catalogs, open-items registers, naming conventions — anything the AI needs grounding from lives in 00-knowledge/. The team owns what goes in and keeps it current. No external integration, no magic.

Built-in compliance and safety

Three layers operate continuously across every stage. None of them require remembering to enable.

KAFI Standard · TT 96/2020

Audit trail
Every interaction logged to audit.md — raw user input, AI response, KB citations, open items, extension compliance. Append-only. ISO 8601. Stored separately from operational data.

KAFI Standard · Decree 13/2023

Personal data privacy
Auto-enables when any artifact touches PII. Adds consent tracking, encryption at rest, access logging, and subject-rights endpoints (access, rectification, erasure, portability).

Soft Enforcement · Warning Mode

AI Review Checklist
Before any meaningful write: grounded · no secrets · scope respected · reversible · human-decidable. Warnings reported in completion summary; team decides whether to proceed.

Workspace Detection chooses the mode automatically. Either can be overridden at any time.

Best for New internal tools, MVPs, isolated greenfield work Extension of existing systems, multi-team, multi-unit, regulated work

Every KAFI project today re-discovers the same context: how KOS-MO is laid out, what the BO Cores do, where TT 96/2020 applies, why a given ADR was made, which open items are still pending. KAI Atlas would be a centralized, always-current knowledge layer that any AI-DLC project queries at Pre-Inception to pull the relevant context — no more manually copying BRDs and architecture docs into 00-knowledge/ by hand.

Name being finalized — KAI Atlas is the working name (sits naturally next to KAI Foundry under the Intelligent Foundation; reads as a map you consult). The kafi-memory skill (v0.8) is the first step toward this: it already mines per-project git history + postmortems for patterns worth promoting to org-level knowledge.
