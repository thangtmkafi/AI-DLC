The KAFI AI-DLC Workflow

An introduction for project leads and teams. How we ship software with AI as the drafter and humans as the deciders.

Audience Leadership · PMs · POs · BAs · SAs · Designers · Devs · DevOps

Software development at KAFI is becoming AI-first. The AI agent drafts artifacts, asks clarifying questions, and generates code. Humans review, decide, and approve at every gate.

AI-DLC isn't about replacing the team. It's about making every role more focused: PMs spend more time on scope decisions, not formatting. BAs spend more time on edge cases, not boilerplate. Devs spend more time reviewing and refining, not typing out scaffolding. Every artifact is in git. Every decision is logged. Every output is reviewable.

Quick install

One terminal command drops AI-DLC into your project folder. The installer auto-detects whether to install fresh or upgrade an existing version, moves any legacy files into 00-knowledge/references/, and downloads the latest release from GitHub. Cross-platform: macOS, Linux, Windows.

macOS / Linux

curl -fsSL https://raw.githubusercontent.com/Kafivn/KORA/main/tools/install.sh | bash

Windows (PowerShell)

iwr -useb https://raw.githubusercontent.com/Kafivn/KORA/main/tools/install.ps1 -OutFile install.ps1
.\install.ps1

Don't run /init. Claude Code already auto-loads CLAUDE.md on every session start. /init is non-destructive (it suggests, not overwrites) but is redundant on an AI-DLC project. The kafi-aidlc-onboarding skill replaces it — see below.

Full installation guide with all flags, scenarios, and troubleshooting: KAFI-Installer-Guide.html

How a session actually works

Every stage follows the same rhythm. Humans decide; the agent drafts and asks; nothing proceeds without explicit approval.

Step 1
Human
Sets intent
PM/PO names what to build. Or a stage owner reviews prior artifacts and decides what's next.
Step 2
AI agent
Drafts + asks
Agent writes a plan with checkboxes and questions in a `[Answer]:` file. Asks measurable, non-vague questions.
Step 3
Human
Reviews + answers
Stage owner fills `[Answer]:` tags, edits artifacts directly if needed, or asks for changes.
Step 4
Human
Approves gate
Two-option message: Request Changes or Continue to Next Stage. No silent progress.

Roles in your project team

Six human roles. Each role has a skill file the agent loads when you're driving a stage that role owns. No QA, Security, or Compliance role in v0.3 — compliance is enforced automatically via extensions.

Product Owner

PM / PO

Owns intent and scope. Authors or validates the Vision Document. Decides what runs and what gets cut.

Drives: Requirements Analysis · Workflow Planning · Pre-Inception D (author from brief)

Business Analyst

BA

Translates intent to requirements and stories. Pushes back on vague language. Uses neutral roles until taxonomy is confirmed.

Drives: Requirements · User Stories · Functional Design · Pre-Inception B/C/D

Solution Architect

Product Designer

Drives: Product Design (only stage UX-led)

Developer

Dev

Pairs with the AI agent on code generation. Reviews the plan, verifies the build, owns the build instructions.

Drives: Code Generation · Build

DevOps / SRE

DevOps

Maps logical components to concrete services. Owns deployment topology and monitoring (Operations is placeholder in v0.3).

Drives: Infrastructure Design · Deployment · Monitoring

How to start a session

After install, you don't manually pick a role or paste a starter prompt. The kafi-aidlc-onboarding skill handles routing — it scans your project, detects current AI-DLC stage, loads the right role guide, and starts the session with a stage-appropriate prompt template.

Working together with git

Six roles plus the AI agent share one repo. The workflow's gates and branches stay in lockstep so parallel work doesn't collide and the audit history is clean. Three rules: stage = branch, gate = pull request, merge = approval.

One branch per stage

Inception stages get their own branch — stage/4-requirements, stage/8-app-design. Construction work groups under unit/UNIT-NN-name. Pre-Inception sub-flows: pre-inception/route-D-vision.

Gate = pull request

The 2-option completion message becomes the PR. Reviewer is the next-stage role or the SA (depending on what's being merged). Approve and merge = gate passed.

Append-only audit log

aidlc-docs/audit.md is append-only on every branch. On merge conflicts: keep both — never overwrite. The full audit history is the TT 96/2020 record.

The folder structure is the contract. The team feeds inputs into 00-knowledge/; the workflow writes outputs into aidlc-docs/, adrs/, and src/. Every stage knows exactly which folders it reads from and writes to.

Built-in compliance and safety

Three layers operate continuously across every stage. None of them require remembering to enable.

KAFI Standard · TT 96/2020

Audit trail
Every interaction logged to audit.md — raw user input, AI response, KB citations, open items, extension compliance. Append-only. ISO 8601. Stored separately from operational data.

KAFI Standard · Decree 13/2023

Personal data privacy
Auto-enables when any artifact touches PII. Adds consent tracking, encryption at rest, access logging, and subject-rights endpoints (access, rectification, erasure, portability).

Soft Enforcement · Warning Mode

AI Review Checklist
Before any meaningful write: grounded · no secrets · scope respected · reversible · human-decidable. Warnings reported in completion summary; team decides whether to proceed.

Idea 1 · v0.4+ · platform layer

System Knowledge Base · a shared brain for every KAFI project

Every KAFI project today re-discovers the same context: how KOS-MO is laid out, what the BO Cores do, where TT 96/2020 applies, why a given ADR was made, which open items are still pending. The SKB would be a centralized, always-current knowledge layer that any AI-DLC project queries at Pre-Inception to pull the relevant context — no more manually copying BRDs and architecture docs into 00-knowledge/ by hand.

Name candidates

Five options. Each plays differently with the existing KAFI naming family (KOS-MO, KAI Foundry, KAI Atlas would be a clean sibling).

KAI Atlas recommended
Atlas of all KAFI systems. Sits naturally next to KAI Foundry under the Intelligent Foundation. Function reads from the name: a map you consult.
KORE
KAFI Operations & Reference Engine. Short, acronymic, fits the CAPS family (KOS-MO, RME, BO). Carries the "core of truth" suggestion.
KAFI Cortex
Brain / neural-system metaphor. Memorable. Suggests the centralized intelligence layer of the firm. Slightly futuristic register.
K-Lens
A looking-glass into the system landscape. Lighter, more product-y. Less formal than the others — could feel right for a self-serve UI.
K-Compass
Guides agents and humans to the right knowledge. Friendly, evocative. Less explicit about "knowledge" than Atlas.

For the rest of this section we use "SKB" as a generic placeholder.

How it would work

The SKB pulls knowledge in from three streams and exposes it through a single MCP server. AI-DLC projects use the MCP both ways — they query at Pre-Inception to inject context, and they push at every stage merge to keep the SKB current.

What the SKB would contain

Anything a future project would need to ground its work, organized by domain and system. Examples — not exhaustive:

System architecture
Per-system layer diagrams, component inventories, integration maps, domain boundaries
API specs
OpenAPI definitions, gRPC contracts, event schemas, versioning history
BRDs & PRDs
Latest business and product requirement docs across systems
Sequence & flow diagrams
Per-capability sequence diagrams · user flows · process diagrams
UI / UX designs
Figma references · screen specs · design tokens · component library state
ADRs
Every architectural decision ever made, with context · rationale · alternatives
Data models
ERDs · table schemas · field dictionaries · PII tags
Open items register
Cross-system pending decisions, owners, status, expected resolution
Compliance mappings
TT 96/2020 · Decree 13/2023 · SSC rules → where they apply, who owns them
Glossary & conventions
KAFI-wide naming, role taxonomy, ID formats, prohibited terms

Integration with AI-DLC

Three concrete additions to the v0.3 workflow:

New skill · kafi-skb
Auto-discoverable like the design-system skill. Tells the agent the SKB exists, what shape it has, and how to query it via MCP.
New rule · pre-inception/0-skb-query.md
Before drafting Vision, the agent queries the SKB MCP for related systems, prior ADRs, and existing capabilities. Surfaces these as starting context — the team decides which apply.
New hook · post-merge update
When a stage PR is merged, a git hook posts the new artifacts to the SKB MCP. Local LLM processes, structures, and embeds. SKB stays current automatically.

Browser chatbot · Local LLM dual purpose

The same Local LLM that ingests artifacts can also answer human questions through a chat panel in the SKB web UI. Same model, two modes: ingestion writes to SKB (existing), inference reads from SKB using RAG — Retrieval-Augmented Generation. Means anyone in KAFI — not just AI-DLC agents — can query the system knowledge directly in the browser.

What people would ask

How the chat flow works

The chat panel does RAG: when a user asks a question, the MCP Server retrieves the most relevant chunks from SKB Core, then prompts the Local LLM with question + retrieved context. The LLM generates a grounded answer with clickable citations back to source artifacts. No hallucination beyond what's in KAFI's actual knowledge — every answer is traceable to a real document in the SKB.

Capacity note · open question. Local LLM serves both ingestion (batch, off-hours friendly) and chat (interactive, latency-sensitive). One DGX Spark unit handles ingestion; the second serves chat inference. To keep chat under ~3 seconds end-to-end, the chat side could run a smaller distilled model (e.g. 8B for retrieval-grounded Q&A) while the heavier 70B model does structured ingestion. Open — pending Phase A benchmarks.

Required infrastructure

SKB storage
Vector DB + graph DB + object/document store. Hosted on-prem under Intelligent Foundation.
MCP Server
Single API surface for query, write, and /chat RAG endpoint. Authenticated, audited every call.
Local LLM
On-prem model serving two modes: structured-knowledge ingestion (heavier 70B for accuracy) and chat inference (smaller distilled model for latency). Sits under KAI Foundry.
Daily scanner
Cron job that walks all KAFI system repos and queues changes for the Local LLM.
Webhook receiver
Listens for AI-DLC merge events. Pulls the diff, hands it to the Local LLM.
Browse UI + chat panel
Web app with chat panel for natural-language Q&A · structured browse of artifacts · clickable citations · (optional) IDE plugin.
Idea 2 · v0.4 · workflow extension

Skill Inventory · pull skills on demand

v0.3 ships a fixed set of skills in the injection package — design-system plus six role guides. Real projects will need more: data-modeling, API-design, accessibility-audit, performance-tuning, integration-testing patterns. A Skill Inventory with its own MCP server would let an AI-DLC project pull the skills it needs at session start, instead of bundling every skill into every project.

How it would work

Central Skill Inventory
All KAFI-approved skills live in one repo. Versioned. Each has metadata: name, scope, prerequisites, supported stages.
Skill MCP server
Lists available skills · fetches a skill on request · returns metadata for the agent to decide.
New rule · skill discovery
In Workspace Detection (or per-stage), the agent queries the Skill MCP for skills relevant to the active stage. Suggests them to the team.
Local cache
Pulled skills land in .claude/skills/ and stay for the project. Skill versions pinned per project for reproducibility.

Open question · who curates

v0.3 hands all skills to the TO. With a Skill Inventory, the TO still owns "approved skill" status, but any team can propose. Needs a lightweight review process — see Idea 3 for candidate skills to seed.
